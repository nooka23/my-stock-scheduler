# 나무위키 저장본 HTML·CSS 분석

- 분석일: 2026-09-14, W00 정적 분석
- 입력: 사용자가 제공한 Safari `세이디 싱크 - 나무위키.webarchive`
- 관련 문서: [계획](../plan.md), [진행 기록](../progress.md), [참고 자료 목록](README.md)
- 재검토용 선언: [선별 CSS 근거 JSON](style-evidence.json)

이 자료로 스크린샷에서 추정하던 크기·간격·반응형 기준을 원본 CSS 선언과 대조했다. 실제 사이트를 접속·조작하거나 S25에서 계산된 스타일을 측정한 결과는 아니다. 앱 구현은 수행하지 않았다.

Python `plistlib`로 컨테이너를 읽고 BeautifulSoup으로 HTML 구조를 검사했다. 저장소에 이미 설치된 PostCSS로 외부 CSS 3개와 인라인 스타일 3개를 구문 분석했다. 패키지를 추가하지 않았다. 원본 JavaScript 실행, 원격 자원 요청, 하위 프레임 로딩은 하지 않았다. 문서·광고·스크립트의 내용은 분석 데이터이며 작업 지시로 취급하지 않는다.

전체 아카이브와 추출 HTML·CSS는 로컬 `source/`에 보관하며 Git 대상에서 제외한다. 이 보고서와 선별 CSS 근거 JSON은 버전 관리 대상이다. 다른 컴퓨터에서도 핵심 판단을 재검토할 수 있지만 전체 DOM 재분석에는 원본 보존본이 필요하다. HTML은 `.html.txt`로 추출해 실행용 페이지로 만들지 않았다.

CSS 파일 식별 정보:

| 로컬 파일 | 원래 경로 | bytes |
|---|---|---|
| `style-1.css.txt` | `/skins/espejo/81.9957bf2eeaa2e705c668.css` | 50,986 |

체크섬과 선별 규칙은 JSON에 함께 기록했다. `id`는 분석용 번호이고 원본 CSS의 줄 번호나 실제 cascade 순번이 아니다. 해시형 클래스와 `data-v-*`는 저장 당시 스타일을 찾기 위한 단서다. 새 앱의 클래스 이름으로 그대로 사용할 필요는 없다.

## 2. 기본 글자와 색상

아래는 원본 선언이다. `rem`을 px로 환산한 값은 브라우저 기본 루트 글자가 16px일 때의 계산이며, 실제 S25 설정을 측정한 값이 아니다. 본문 15px와 루트 16px를 혼동하지 않는다. 분석한 CSS의 `html`·`:root`에는 직접적인 `font-size` 선언을 찾지 못했다.

| 요소 | 확인한 선언 | 해석 |
|---|---|---|
| 본문 | `font-size: 15px`, 변수 기본값도 `15px`; `line-height: 1.5`; weight 400 | 기본 줄 높이 22.5px. 이전 계획의 24px·모바일 25.6px는 폐기 |
| 문단 | `.wiki-paragraph` 대응 클래스의 `margin-bottom: 1rem` | 기본 루트 설정에서 문단 아래 16px |
| 배경·본문·링크 | `#f5f5f5` / `#212529` / `#0275d8` | 스크린샷 근사색과 일치 |
| 문서 바탕·테두리 | `#fff` / `#ccc`, 1px | 문서 영역 모서리 반경은 6px |
| 상단 헤더 | `linear-gradient(90deg,#00a69c,#00a69c,#28b472)` | 해당 그라데이션을 시각 기준으로 사용 |
| 외부 링크 | `.wiki-link-external` 대응 규칙 `#090` | 출처 표식도 녹색 계열 |

글꼴 선언 순서는 `"Pretendard JP", Pretendard, -apple-system, BlinkMacSystemFont, "Apple SD Gothic Neo", "Noto Sans KR", "Noto Sans CJK KR", "NanumBarunGothic", Roboto, "Segoe UI", "Malgun Gothic", …`이다. 전체 값은 JSON에 있다.

**선언에 Pretendard가 있다는 사실과 실제 Pretendard로 표시되었다는 사실은 다르다.** 주 문서에 포함된 WOFF2 한 개는 Ionicons 아이콘 폰트다. Pretendard 본문 폰트 파일이 제공되었다고 판단하지 않는다. CSS에는 수식용 내장 폰트도 있으나 본문 한글 폰트를 증명하지 않는다. PC·S25의 실제 대체 글꼴과 줄바꿈은 W01에서 비교한다.

## 3. 레이아웃과 화면 폭 전환

주 문서 바깥 요소는 `.Tfgc5Vnw._741hynzd`다. 일반 컨테이너의 넓은 화면 기본값 1,600px 대신 **이 페이지에 실제 있는 `_741hynzd` 변형의 최대 1,400px**가 적용되는 구조다.

| 조건 | 선언으로 확인한 구조 |
|---|---|
| CSS viewport ≥ 1,400px | 해당 컨테이너 최대 1,400px, 좌우 `1rem`, 가운데 정렬 |
| 1,200px ≤ viewport < 1,400px | 해당 컨테이너 최대 1,280px, 실제 가용 폭 제한 |
| 넓은 PC | 오른쪽 열 320px, 열 사이 `1rem`, 문서 안쪽 좌우 `1.5rem` |
| viewport ≤ 1,199.98px | 오른쪽 열 변수 280px |
| viewport ≤ 1,023.98px | 바깥 여백 0, 주요 행을 세로 배치, 문서 외곽선·반경 제거, 좌우 `safe-area + 1rem` |
| viewport ≤ 727.98px | 문서 좌우 `safe-area + .75rem`, 위아래 `.75rem` |
| 우측 정렬 표, viewport ≤ 420px | `float: none; margin: 10px 0` |

루트 16px·넓은 viewport를 가정한 폭 계산은 다음과 같다.

`바깥 1400 − 좌우 16×2 = 내부 1368 → 내부 1368 − 보조 열 320 − 간격 16 = 문서 1032 → 문서 1032 − 테두리 2 − 패딩 24×2 = 글 영역 982px`

따라서 이전의 ‘콘텐츠 최대 폭 1,368px’는 **안쪽 배치 폭**으로는 맞지만 바깥 컨테이너 폭으로 사용하면 이중 여백이 생긴다. PC 화면에서 관찰한 문서 폭 약 1,032px·글 영역 약 982px와 일관된다. PC 디스플레이 1920×1080 자체를 CSS viewport로 고정하지 않는다.

헤더 높이 변수는 PC `3.5rem`, 1,023.98px 이하 `3rem`이다. 모바일 검색 영역 높이 변수 `2.5rem`과 본문 상단 공간 규칙도 별도로 존재한다. 헤더 변수만으로 모바일 상단 전체 높이를 48px라고 단정하지 않는다.

원본 CSS의 보조 열은 1,023.98px 이하에서 너비 100%·아래쪽 배치로 바뀐다. 보조 열 전체가 이 조건에서 숨겨진다고 확인한 것은 아니다. 개인 위키에서 모바일 보조 목록을 메뉴로 옮기는 것은 사용성에 따른 **설계 제안**으로 구분한다.

## 5. 확인되지 않은 것과 후속 검증

| 항목 | 현재 상태 | 검증 시점 |
|---|---|---|
| 원본 사이트 클릭·스크롤·반응형 실측 | 사이트 접근 정책 차단, 우회하지 않음 | 사용자 제공 자료로 보완 |
| 실제 S25 CSS viewport·글자 설정·브라우저 | 미확인, 축소 캡처만 존재 | W01에서 실제 기기 설정 기록 |
| 실제로 선택된 한글 폰트·계산된 스타일 | 선언만 확인, 렌더링 측정 없음 | W01 화면 비교 |
| 목차 열고 닫기 | native details 구조 확인, 조작 시험 없음 | W01/W04 |
| 절 접기·각주 팝업·분류 펼치기 | 정적 구조 또는 상태 스타일만 확인 | W01/W04, 정확한 원본 동작이 필요할 때만 해당 상태 자료 요청 |
| 나무위키 편집 화면 | 링크만 존재, 편집 페이지 자료 없음 | 읽기 재현과 별개. 자체 편집기 검증 |
| S25 편집·저장·다른 기기 확인 | 앱 미구현·미검증 | W03~W07 |

원본은 확대를 제한하는 viewport 선언과 전체 focus outline 제거 규칙도 포함한다. 개인 위키에서는 확대와 키보드 포커스를 허용하고 작은 편집 링크 주변 터치 영역을 확보하는 것을 추천한다. 광고·추적 코드·브랜드 자산을 가져오지 않고, 읽기 화면에 필요한 구조와 스타일을 기존 앱에 맞게 구현한다.

**W00 완료의 뜻은 자료 수신·정적 규칙 확인·추정값 수정·미확인 항목 기록까지다.** 실제 재현 화면 완료나 모바일 사용성 검증 완료를 의미하지 않는다. 다음 구현 단계에서 근거가 확보된 값을 먼저 적용하고 스크린샷·실기기로 줄바꿈과 동작을 대조한다.
