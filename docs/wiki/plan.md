## 목적과 성공 기준

한국 주식 전업투자자가 기업·산업·테마 자료를 자유롭게 작성하고 내부 링크로 연결하는 개인 위키를 기존 웹사이트에 추가한다. 서버를 원본으로 삼는 새 위키이며 필요한 기존 자료부터 수동으로 가져온다.

핵심 성공 기준:

1. 밖에서도 갤럭시 S25로 자료를 찾고, 메모·수정·서버 저장을 끝내고, PC에서 같은 내용을 확인할 수 있다.
2. 나무위키처럼 익숙하고 읽기 편해 자주 들어가 작업하고 싶은 공간이 된다.

### 사용자가 명시적으로 확정한 조건

- 별도 사이트를 새로 만들지 않고 현재 사이트에 위키 영역을 추가한다.
- 첫 사용자는 본인 한 명이다. 다른 이용자는 위키를 사용하거나 볼 수 없다.
- 모바일은 갤럭시 S25를 우선한다. PC 기준 디스플레이는 1920×1080이다.
- 나무위키의 레이아웃과 시각적 표현을 최대한 충실하게 재현한다. 로고와 이름은 개인 위키의 것을 쓴다.
- 문서 본문은 자유 형식이다. 기업 개요·투자 포인트·리스크 같은 고정 섹션을 강제하지 않는다.
- 필수 입력은 제목 등 최소한으로 제한하고 종목코드·분류는 선택적으로 둔다.
- 볼트 전체 이전, Obsidian 양방향 동기화, AI 자동 정리는 초기 범위가 아니다.
- 외장 하드는 사용자가 나중에 마련한다.
- 2026-09-14 현재까지의 요청은 조사·계획 수정·문서화다. 기능 구현은 아직 요청하지 않았다.

### 설계에 영향을 주는 사항

- 루트 `body`와 자식 래퍼에 `h-screen`, `overflow-hidden`이 있다. 위키 하위 레이아웃만 추가해서는 상위 스크롤 제한이 해소되지 않는다.
- `Sidebar.tsx`는 이름과 달리 공통 상단 내비게이션을 렌더링한다.
- 미들웨어 matcher는 `/`, `/login`뿐이다. 위키 경로·API는 새로 보호해야 한다.
- 기존 종목 검색 API는 공개 기업 데이터용이다. 위키 검색에 인증 없이 복사해서 사용하지 않는다.
- 기존 로그아웃은 `localStorage`와 `sessionStorage`를 전체 비운다. 위키 초안은 사용자 전환·명시적 로그아웃·세션 만료를 구분해 다뤄야 한다.
- 최신 infra 기록에는 Realtime·Edge Functions 제거, Storage 이미지 변환 비활성화가 있다. 첫 버전은 이 서비스들을 다시 활성화하지 않아도 구현 가능하다.
- 기존 DB 백업은 `public`, `auth`, `storage` 메타데이터를 포함하고 파일 본문은 별도 Storage 백업을 사용한다. 기존 스크립트에는 7일 지난 백업 정리 동작이 있다.
- `next.config.ts`에는 타입 오류를 무시하는 설정이 있다. 빌드 성공만으로 타입 검증 통과라고 판단하지 않는다.

### 조사 한계

실행 중인 Docker 컨테이너 조회는 소켓 접근 권한 제한으로 실패했다. Vercel의 현재 배포 환경변수와 운영 DB의 실제 정책은 직접 검증하지 않았다. 정기 백업의 최근 실행·외부 보관·전체 복원 성공도 확인되지 않았다. 위의 운영 판단은 파일과 운영 기록에 근거하며, 실제 적용 전 상태를 다시 확인해야 한다.

## 2. 위키 경로와 기존 사이트 연결 방식

제안 경로:

| 경로 | 역할 |
|---|---|
| `/wiki` | 검색·최근 수정 문서·분류·새 문서 |
| `/wiki/categories` | 사용 중인 분류 목록·분류별 문서 모아보기·종목 일괄 분류 |
| `/wiki/categories?name=…` | 선택한 분류의 문서·추가할 종목 검색 |
| `/wiki/new` | 새 문서·빠른 메모 |
| `/wiki/d/[id]` | 문서 읽기 |
| `/wiki/d/[id]/edit` | 전체 편집 |
| `/wiki/d/[id]/edit?section=[headingId]` | 제목으로 구분되는 절 편집 |
| `/wiki/d/[id]/history` | 이력·이전 버전·복구 |
| `/wiki/search?q=…` | 제목·본문 검색 |
| `/wiki/settings` | 내보내기·백업 상태 |

제목 변경에도 주소와 링크가 유지되도록 문서 ID를 주소의 기준으로 둔다.

- 기존 메뉴의 위키 항목은 본인에게만 표시하고, 직접 URL·API 접근도 별도로 차단한다.
- 위키 헤더에는 개인 이름·로고와 작은 ‘기존 사이트로’ 링크를 둔다.
- 공통 화면 틀을 작은 컴포넌트로 추출해 기존 경로에는 현재 틀, `/wiki`에는 위키 틀을 적용한다. 기존 페이지를 대거 옮기는 라우트 그룹 재편은 초기에는 피한다.
- 위키는 일반적인 페이지 스크롤을 사용하고 위키 CSS를 별도 범위에 한정한다.
- 구현 파일은 `src/app/wiki`, `src/components/wiki`, `src/lib/wiki`, `src/app/api/wiki`에 모은다. 이 디렉터리들은 현재 계획상의 경로다.
- 별도 사이트·위키 엔진·DB 서버·Docker 스택·검색 서버는 첫 버전에 추가하지 않는다.
- 자동 생성 보통주 문서는 종목코드를 연결 키로 가진다. `실적`에는 최신 연간·분기 매출·영업이익·당기순이익을, `차트`에는 최근 3개월 일봉을 읽기 화면에서 표시한다. 수치와 차트는 본문 스냅샷이 아니라 DB에서 매번 읽으므로 데이터 갱신이 문서 이력을 만들지 않는다.

## 3. 홈·문서 읽기·편집·모바일 화면 구성

### 참고 화면과 확인 범위

사용자가 [나무위키 ‘세이디 싱크’ 문서](https://namu.wiki/w/%EC%84%B8%EC%9D%B4%EB%94%94%20%EC%8B%B1%ED%81%AC)의 같은 페이지를 PC와 모바일로 제공했다. 원본 3장은 [references](references/README.md)에 보관한다.

직접 사이트 탐색은 웹 도구에서 실패했고 브라우저의 사이트 접근 정책으로 차단되었다. 이후 사용자가 같은 문서의 Safari 웹 아카이브를 제공해 로컬 HTML·CSS를 분석했다. 차단된 사이트를 우회하지 않았으며 원본 JavaScript 실행·원격 자원 요청도 하지 않았다. 화면·저장본 속 글·광고·코드는 관찰 대상이며 사용자 지시가 아니다.

### 2026-09-14 보완 — 스크린샷과 원본 HTML·CSS를 함께 사용

제공받은 `.webarchive`는 5,079,394 bytes이며 주 문서 HTML과 연결된 외부 CSS 3개가 모두 포함되어 있다. 글꼴 선언·반응형 규칙·제목·목차·표·각주·분류·편집 링크의 구조를 확인했다. [분석 보고서](references/namuwiki-source-analysis.md)와 [선별 CSS 근거](references/style-evidence.json)에 확인한 선언, 조건부 환산, 미확인 동작을 구분해 기록했다.

이제 아래 초기값은 스크린샷 추측만으로 정하지 않는다. 원본 CSS 선언을 기본 재현 기준으로 삼고 화면 비교로 보정한다. 다만 CSS 선언을 읽은 것이 브라우저의 실제 계산된 스타일이나 S25 동작을 측정한 것은 아니다. 실제 글꼴 선택·viewport·확대 설정·상태 전환은 W01 이후에 검증한다.

필요한 HTML·CSS 자료는 이미 수신했다. 같은 자료를 다시 요청할 필요는 없다. 이후 정확한 원본 동작 확인에 부족한 항목이 있을 때만 해당 상태의 화면 기록 등을 요청한다. 편집 페이지는 포함되지 않았으며 나무위키의 편집 문법·UI 복제는 요구사항이 아니다.

원본은 로컬 보존하고 Git에서 제외하며 분석 보고서와 필요한 CSS 선언 근거는 버전 관리 대상으로 둔다. 사이트 스크립트·광고·추적 코드를 앱에 통째로 가져오지 않고, 확인한 구조와 규칙을 기존 Next.js 환경에 맞게 구현한다. 스크린샷은 최종 화면 비교 기준으로 함께 유지한다. 기능 구현은 최신 사용자 요청 범위를 따른다.

### PC에서 확인한 시각적 특징

- 연한 회색 배경 위에 흰 문서 영역과 좁은 오른쪽 보조 열.
- 청록색에서 녹색으로 이어지는 상단 헤더.
- 왼쪽 문서 제목·수정 시각, 오른쪽 문서 도구.
- 본문 앞의 얇은 분류 표시줄.
- 작은 직사각형 테두리 목차, 단계별 번호와 들여쓰기.

글꼴 선언은 Pretendard JP·Pretendard 다음 Apple·Noto·Roboto·맑은 고딕 등으로 이어진다. 실제 적용된 글꼴은 미확인이다. 아카이브의 WOFF2는 아이콘 폰트이므로 Pretendard 본문 파일을 확보했다고 판단하지 않는다. 전체 선언을 참고하되 W01에서 S25의 실제 한글 글꼴·줄바꿈을 비교해 선택한다.

### 화면 구성 제안

| 화면 | 구성 |
|---|---|
| 홈 | 문서와 같은 흰 영역에 검색, 새 문서·빠른 메모, 최근 수정, 분류별 문서 링크를 목록으로 배치 |
| 문서 상단 | 제목·수정 시각·비공개 상태, `편집 / 역사 / 더보기`, 선택적 분류 표시줄 |
| 읽기 본문 | 자동 목차, 자유 본문, 절별 `[편집]`, 표·이미지·출처·각주 |
| 보조 열 | 내 최근 수정 문서와 분류 목록 |
| 전체 편집 | 제목·본문 중심, 최소 도구 모음, 미리보기·저장 상태·저장 버튼, 접힌 선택 메타데이터 |
| 문서 이동 | 작은 목차·위로 이동 도구 |

광고, 토론, 실시간 검색어는 제외한다. 제목 아래 큰 빈 공간도 개인 위키에서는 유지하지 않는다. 해당 공백의 원인을 스크린샷만으로 광고 슬롯이라고 확정한 것은 아니다.

### 분류별 모아보기·여러 문서 일괄 지정

현재 분류는 문서의 `categories text[]` 값으로 저장된다. 생성·편집 화면에서 쉼표로 직접 입력한다. 문서 읽기 화면의 분류 링크는 `/wiki/search?q=분류`로 연결되지만, 검색 화면은 제목과 본문만 검색하고 분류 배열은 조건에 넣지 않는다. 따라서 현재 분류 링크는 분류 전용 모아보기로 동작하지 않는다.

구현 동작:

- 위키 홈·상단 메뉴에 분류 진입점을 두고 `/wiki/categories`에 사용 중인 분류명과 문서 수를 나열한다.
- 분류를 열면 해당 분류가 붙은 문서를 제목·종목코드·최근 수정일과 함께 보여준다. 분류 문서는 50개씩 페이지로 불러온다.
- 분류 목록에서 새 이름으로 진입하거나 분류 화면의 `문서 추가`를 눌러 종목명·종목코드로 검색하고 여러 개 선택해 한 번에 추가한다. 예: `로봇`을 선택 → `레인보우로보틱스`, `두산로보틱스` 체크 → `로봇 분류 추가`.
- 새 분류는 첫 문서에 추가할 때 생성된다. 기존 분류는 보존하고 선택 분류만 추가한다. 이미 같은 분류가 있는 문서는 중복 추가하지 않는다. 분류 제거는 별도 기능이다.
- 문서의 분류 링크는 일반 본문 검색이 아니라 해당 분류 문서 목록을 연다. 여러 분류 조합 필터는 첫 구현에서 제외한다.
- S25에서는 분류 선택·문서 검색·체크·하단 고정 `선택 문서에 분류 추가` 버튼으로 조작한다. 검색은 제목/종목코드를 서버에서 조회해 결과를 제한한다.

분류 변경은 서버의 원자적 일괄 처리 함수가 수행한다. 대상 문서의 소유자 접근을 검사하고 `categories`만 변경한 뒤 문서별 revision 스냅샷을 남긴다. 전체 작업이 실패하면 모두 롤백된다. mutation ID로 재시도 중복을 막고, 기존 분류가 중복되지 않게 한다. 인증된 본인 사용자만 분류 통계 조회와 일괄 변경을 호출할 수 있다.

첨부 화면의 갈색 배우 프로필 표는 해당 문서의 내용이다. 기업별 필수 정보 상자로 일반화하지 않는다. 기본 문서는 자유 본문이며 사용자가 원할 때 일반 표·이미지의 간단한 우측 배치를 제공한다. 여러 블록을 묶는 복잡한 정보 상자는 후속이다.

목차 번호는 제목 계층을 따라 `1`, `1.1`, `1.2`, `1.2.1`처럼 자동 계산한다. 같은 단계의 하위 제목 수는 제한하지 않는다. 제목 단계는 편집기에서 H2~H6까지 선택할 수 있고, HTML 제목 단계의 깊이(H6까지)는 유지한다. 번호는 표시용이며 내부 앵커는 제목 고유 ID를 사용한다. 번호 매김 기준은 해당 문서에서 가장 얕은 제목 단계로 하여 기존 H2 기반 템플릿과 상위 제목이 없는 문서를 모두 지원한다. 내부 링크는 파란색, 각주는 위첨자 번호로 표시한다. 분류는 선택적으로 입력한 경우만 얇은 링크 표시줄로 보여준다. 문단별 편집 링크는 제목 줄 오른쪽에 둔다.

### 갤럭시 S25 우선 구성

첨부 화면에서 관찰한 순서:

`작은 사이트 헤더 → 제목·수정 정보 → 문서 도구 → 분류 → 이미지·정보 표 → 목차 → 본문`

PC에서 오른쪽에 있던 표는 모바일에서 전체 폭으로 내려오고 그 뒤에 목차가 나온다. 선두 우측 배치 이미지·표가 있을 때 이 순서를 따른다. 해당 요소가 없는 문서에 빈 공간이나 필수 양식을 생성하지 않는다. 안드로이드 상태바와 브라우저 주소창은 사이트 UI 재현 대상이 아니다.

모바일 초기값 제안:

- 1023.98px 이하 한 열·바깥 여백 0. 본문 좌우는 727.98px 이하 safe-area + .75rem(기본12px), 그보다 넓은 모바일 구간은 safe-area + 1rem(기본16px).
- 원본 기본값인 본문 15px·line-height 1.5, 문서 제목 2rem(기본 32px), h2 1.8em(기본 27px)을 우선 적용한다. 종전 16px·25.6px·28px 제안은 대체한다.
- 본문 전체의 가로 스크롤은 피하고 넓은 표에만 가로 스크롤 적용.
- 개인 위키에서는 오른쪽 보조 열의 목록을 메뉴로 옮기는 것을 제안한다. 원본 CSS는 좁은 화면에서 보조 열을 아래로 배치하며, 전체 숨김으로 확인된 것은 아니다.
- 작은 `[편집]` 표현을 유지하되 주변 터치 영역 확보.
- 편집 화면은 키보드가 열린 상태에서도 저장 버튼에 접근 가능.
- 읽기 화면에는 편집기를 로드하지 않고 필요할 때만 편집기를 연다.

모바일 파일은 **163×1,280px로 축소**되어 viewport·터치 영역을 판독할 수 없다. 글자·간격은 원본 CSS로 보완했지만 실제 S25에서 조정할 시작값이다. 우측 표의 float 해제 기준은 원본에서 420px 이하이며 기종명으로 viewport를 단정하지 않는다. 삼성 인터넷과 Chrome을 검증 대상으로 하고 실제 주 사용 브라우저를 우선한다. 다른 기기는 기본 반응형을 유지하되 세부 최적화는 후속이다.

목차의 native details 구조·각주 앵커·절 접기 상태 CSS·절 편집 링크는 원본에서 확인했다. 각주 팝업의 실제 작동·절 접기 조작·모바일 편집 화면은 미검증이다. 각주 탭·본문 복귀·절 접기를 제안 동작으로 두고 실제 조작을 확인했다고 기록하지 않는다. 원본의 확대 제한과 전체 focus outline 제거는 따르지 않고 확대·키보드 포커스·터치 영역을 확보한다.

## 4. 편집기·저장 형식과 핵심 선택 이유

추천안은 **Tiptap + 구조화된 JSON 원본 + Markdown·첨부 내보내기**다. 아직 설치·통합하지 않았다.

| 대안 | 판단 |
|---|---|
| Markdown 텍스트 원본 편집 | 이식성은 좋지만 휴대폰의 표·이미지·링크 편집 부담이 큼 |
| Tiptap + JSON | 기존 React/Next.js와 통합하고 표·링크·고유 제목 ID를 다루기 적합 |
| HTML 원본 | 문단 식별·변환·검증 기준 관리가 어려워질 수 있음 |

Tiptap의 기본 UI를 그대로 쓰는 것이 아니라 읽기 렌더러를 따로 구성한다. JSON 형식 버전과 지원 요소를 명시해 편집기 의존성을 관리한다. Tiptap의 공식 Markdown 기능은 조사 시점 Beta였으므로 임의 문서의 완전한 왕복 변환을 전제하지 않는다. 읽을 수 있는 Markdown과 보존용 JSON을 함께 제공한다.

### 첫 지원 요소

제목, 문단, 목록, 강조, 기본 표, 이미지, 내부·외부 링크, 기본 각주를 지원한다. 표는 행·열 추가/삭제와 헤더를 우선하고 셀 병합·중첩 표는 후속으로 둔다. 이미지 업로드·실패·재시도는 편집기의 이미지 표시 확장과 별도로 구현한다.

### 문단별 편집 — 첫 버전 포함 추천

문단은 제목으로 구분되는 절 단위다.

1. 제목에 고유 ID를 부여한다. 맨 앞의 제목 없는 도입부는 별도 구간으로 다룬다.
2. 선택한 제목부터 다음 동일·상위 단계 제목 직전까지를 편집한다.
3. 저장 시 문서 전체 버전을 검사하고 해당 구간만 교체한다.
4. 목차·각주 번호·검색 텍스트·링크 색인을 갱신하고 전체 수정 이력을 남긴다.
5. 읽기 화면의 원래 위치로 복귀한다.

대상 절의 단계 변경, 절 간 이동·재구성은 전체 편집에서만 허용한다. 서로 다른 절을 편집했더라도 첫 버전에서는 자동 병합하지 않는다. 전체 편집 완성 후 추가 약 4~7 개발일이라는 초기 추정이며, 실제 편집기 시험 후 재산정한다. 모바일 긴 문서 수정에 직접 기여해 우선순위가 높다.

### 초안·저장·기기 전환

- 사용자·문서별 IndexedDB 초안을 보존하고 세션 만료나 저장 실패만으로 지우지 않는다.
- `수정 중 → 기기에 초안 보관 → 서버 저장 중 → 서버 저장 완료`를 구분한다. 다른 기기에 보이는 것은 서버 저장 완료된 내용이다.
- 요청 시 `base_revision`을 전송하고 DB에서 검사한다. 불일치하면 충돌로 처리하고 내 초안을 보존한 채 최신본과 비교하게 한다.
- `mutation_id`를 사용해 DB 저장 후 응답 유실·재시도에서 이력이 중복 생성되지 않게 한다.
- 저장 응답 대기 중 추가 입력한 내용을 과거 요청의 성공으로 덮어쓰거나 초안에서 지우지 않는다.
- 문서 재진입·앱 복귀 시 최신 버전을 확인한다. 편집 중인 내용을 자동 교체하지 않는다.
- 명시적 로그아웃 때는 미저장 내용 처리 후 계정별 초안·인증된 이미지 표시 자원을 정리한다. 계정 전환 때 다른 계정의 초안을 노출하지 않는다.
- 초기에는 미저장 초안의 기기 간 동기화나 완전한 오프라인 위키를 제공하지 않는다.

### 갤럭시 S25 편집 검증

한글 조합·커서 이동·텍스트 선택, 긴 문서에서 절 진입, 표 셀 입력·행 추가, 갤러리 업로드·재시도, 내부 링크 검색 후 입력 보존, 키보드 열기/닫기·화면 회전 후 편집 위치를 실제 기기에서 확인한다.

## 5. 문서·링크·첨부파일·이력의 최소 데이터 구조

기존 백업 범위에 포함하도록 `public` 스키마의 `wiki_` 접두사 테이블을 추천한다. 아래는 개념 설계이며 마이그레이션은 아직 없다.

| 테이블 | 최소 정보 |
|---|---|
| `wiki_documents` | UUID, 소유자, 제목, 본문 JSON, 검색용 텍스트, 형식 버전, 현재 수정 버전, 선택적 종목코드·분류, 생성·수정 시각 |
| `wiki_document_names` | 소유자, 정규화된 현재·이전 제목, 대상 문서 ID |
| `wiki_links` | 출발 문서·링크 위치, 대상 문서 ID, 선택적 제목 ID, 미생성 문서의 임시 제목 |
| `wiki_attachments` | 첨부 ID, 소유자, Storage 경로, 원래 파일명, MIME·크기·체크섬·업로드 상태 |
| `wiki_revisions` | 문서 ID·버전, 제목·본문·선택 메타데이터 스냅샷, 첨부 참조, 작성자·시각, 복구 원본 버전, 저장 요청 ID |
| `wiki_access` | 본인 계정 UUID를 지정하는 관리용 단일 설정. 일반 사용자는 변경 불가 |

### 일관성 규칙

- 제목만 필수이고 본문은 비어 있어도 된다. 종목·분류·기업 유형·분석 섹션을 필수화하지 않는다.
- 현재 제목과 이전 제목의 이름 공간을 함께 관리해 충돌을 막는다. 제목 변경 후에도 ID 링크와 이전 제목 검색을 유지한다.
- 표시 문구가 다른 내부 링크를 지원하고 미생성 문서 링크는 생성 후 같은 위키 안에서 연결한다.
- 검색용 텍스트·링크 색인은 JSON 본문에서 생성하는 파생 데이터다.
- 본문·현재 버전·이력·검색 텍스트·링크 갱신을 하나의 DB 트랜잭션으로 처리한다.
- 직접 갱신으로 버전 검사나 이력 생성을 우회하지 못하도록 쓰기 경로와 권한을 설계한다.
- 이전 버전 복구는 새 버전을 생성한다. 과거 기록은 지우지 않는다. 제목까지 복구할 때 이름 충돌을 검사한다.
- 본문에는 임시 URL이 아닌 첨부 ID를 저장하고, 과거 이력이 참조하는 파일은 즉시 삭제하지 않는다. 파일 교체는 새 객체로 저장한다.

### 종목 마스터 기반 문서 생성·이름 동기화

- `companies.code`를 기업 문서와 종목 마스터 사이의 불변 연결 키로 사용하고 `(owner_id, ticker_code)` 중복을 막는다. 문서 주소와 내부 링크는 계속 문서 UUID를 사용한다.
- 초기 동기화는 종목코드가 없는 문서만 새로 만들며, 이미 같은 종목코드가 연결된 문서는 재사용한다. 본문은 빈 Tiptap 문서로 시작한다.
- 자동 생성 당시 제목과 현재 문서 제목이 같은 경우에만 `companies.name` 변경을 자동 반영한다. 사용자가 제목을 직접 바꾼 문서는 덮어쓰지 않고 불일치 목록으로 남긴다.
- 자동 제목 변경도 저장 함수와 수정 이력을 거치며 이전 제목은 `wiki_document_names`의 별칭으로 유지한다. 따라서 종목명이 바뀌어도 문서 UUID와 기존 내부 링크는 유지된다.
- 상장폐지·마스터 제외는 문서를 삭제하지 않고 비활성 상태로 표시한다. 사용자가 쓴 본문과 이력은 그대로 보존한다.
- 일괄 작업은 여러 번 실행해도 결과가 같은 멱등 작업으로 만들고, 실제 생성·변경·건너뜀 수를 실행 기록에 남긴다.

### 본인 계정만 접근

다음 두 조건을 모두 검사한다.

1. `auth.uid()`가 운영자가 등록한 위키 허용 UUID와 일치한다.
2. 대상 문서·이력·첨부파일이 그 사용자 소유다.

단순히 `owner_id = auth.uid()`만 적용하면 다른 사용자가 자신의 위키를 만들 수 있으므로 충분하지 않다. 메뉴 노출, 서버 페이지, API, DB RLS, Storage 정책, 검색·자동완성·내보내기에 허용 계정 제한을 적용한다. 다른 웹사이트 관리자 계정에도 우회 권한을 부여하지 않는다. 서비스 역할 키·운영 DB 권한은 브라우저에 제공하지 않는다.

`wiki_access`를 읽는 서버·DB 접근 판정이 같은 설정을 사용하도록 하고, 일반 사용자가 프로필이나 요청값으로 허용 대상을 바꿀 수 없게 한다. 페이지가 숨겨져 있다는 것만으로 권한 검증 완료로 보지 않는다.

첨부파일은 비공개 Storage에서 사용자 인증을 포함해 다운로드하고 로그인한 브라우저에 표시한다. 초기 계획의 단기 서명 URL 기본안은 본인 전용 조건 강화 후 제외했다. 파일 주소를 다른 계정이나 비로그인 상태에서 열어도 다운로드할 수 없는지 확인한다. 공용 응답 캐시·공개 이미지 최적화·공개 검색 색인에 위키 데이터를 넣지 않는다.

기존 Supabase 계정은 유지한다. 서버에서 실제 사용자 확인을 수행하고, 구형 auth-helpers와 새 클라이언트를 무계획하게 혼용하지 않는다. 공통 인증 래퍼·세션 갱신을 공식 SSR 구성으로 정리하는 작업은 별도 검증 단위로 진행하고 기존 로그인·로그아웃·비밀번호 관련 흐름을 회귀 확인한다.

### 검색

PostgreSQL의 제목·이전 제목·본문 부분 검색부터 시작한다. 제목 정확 일치 → 제목 포함 → 본문 포함 순서로 정렬하고 안전하게 렌더링한 문맥 일부를 보여준다. 본문만 등장하는 검색어와 한글 한두 글자·영문·종목코드를 확인한다. 문서량이 늘면 `pg_trgm` 인덱스를 검토하되 짧은 검색어 성능을 별도 측정한다. 검색에 공개 기업 검색 API의 무인증 접근 방식을 재사용하지 않는다.

빠른 메모는 별도 데이터 유형 없이 일반 문서로 저장하고 임시 제목을 제안한다. Obsidian은 필요한 문서의 붙여넣기·단일 Markdown 수동 가져오기 수준으로 시작한다. 이미지·내부 링크의 변환 결과를 확인하며, 플러그인 문법 전체 지원은 하지 않는다.

공개 공유는 첫 버전에서 제외한다. 향후 별도 문서 공유 권한을 설계할 여지를 두되, 공유 문서가 참조하는 다른 문서·이력·이미지까지 자동으로 공개하는 설계는 하지 않는다.

### 외장 하드 마련 전 백업

아래 주기·보존 기간은 AI 추천 잠정값이며 사용자가 개별 확정한 수치는 아니다.

- 서버의 별도 백업 디렉터리에 DB와 첨부파일을 보관한다.
- 하루 1회, 최근 7일 보관을 임시 기본안으로 둔다. 이 주기에서는 서버 장애 시 최대 하루치 변경 손실 가능성을 감안한다.
- 기존 스크립트의 정리 동작을 확인하고, 새 백업 검증 없이 마지막 정상 복구본을 삭제하지 않는다.
- 파일 생성·아카이브 읽기·참조 첨부 누락을 검사하고 최근 성공 시각을 기록한다.
- 격리된 DB·Storage에서 문서·파일·이력·소유권·로그인·접근 권한을 복원한다.
- 같은 저장장치의 백업은 장치 고장까지 대비하지 못한다. 외부 복구본 확보와 구분한다.
- 외장 하드 없이도 구현·시범 사용은 진행 가능하다. 외부 백업 완료로 기록하지 않는다.

### 외장 하드 마련 후 백업

- 장치와 마운트 위치를 식별한 뒤 외장 하드에 추가 복사한다.
- 장치 미연결 시 기록을 남기고 로컬 백업을 유지한다. 외장 하드 대신 서버의 빈 마운트 디렉터리에 쓰지 않도록 확인한다.
- 복사·체크섬 검증 후 성공 처리한다.
- 일별 30개·주별 12개 보관을 기준으로 용량을 확인한다.
- 외장 하드의 복구본으로 격리 환경 복원 시험을 수행한다.

DB 백업은 Storage 파일 본문을 포함하지 않는다. DB 스냅샷이 참조하는 첨부를 함께 확보하고, 파일을 덮어쓰거나 이력 참조 파일을 조기 삭제하지 않아 일관된 복구본을 만들 수 있게 한다. 운영 DB에 복구 스크립트를 시험 실행하지 않는다.

### 내보내기

ZIP에 Markdown, 원본 JSON과 형식 버전, 첨부파일 원본, 문서 ID↔파일명 manifest, 이력 JSON을 포함한다. 내부 링크·이미지는 상대 경로로 변환하고 외부 출처 URL은 유지한다. 만료되는 인증 URL을 내보낸 문서의 이미지 주소로 쓰지 않는다.

서비스에 접속하지 않고 Markdown과 파일을 읽을 수 있고, 원본 JSON·첨부로 검증 환경을 재구성할 수 있어야 한다. 복잡한 편집기 요소를 Markdown만으로 손실 없이 보존한다고 주장하지 않는다. 대규모 가져오기 UI 대신 검증용 관리 도구로 복원 가능성을 확인한다.

### 핵심 인수 시나리오

1. 외부 이동통신망의 S25에서 본문에만 있는 단어로 문서를 찾는다.
2. 긴 문서의 해당 절에 한글 메모와 출처 링크를 추가한다.
3. 저장 중 통신이 끊겨도 초안이 남고 재시도로 서버 저장을 완료한다.
4. PC에서 동일한 내용을 확인한다.
5. PC의 오래된 편집본 저장은 충돌로 처리되고 휴대폰 수정이 사라지지 않는다.
6. 이전 버전의 본문·메타데이터·이미지를 열람하고 새 이력으로 복구한다.
7. 다른 사용자·다른 관리자·비로그인 상태에서 문서·검색·자동완성·이력·파일·내보내기 접근을 직접 시도해 차단을 확인한다.
8. 백업 또는 원본 내보내기로 격리 환경에서 내용·파일·권한을 복원한다.

구현 검증은 `npm run lint`, `npm run build`, 필요한 타입 검증과 권한·충돌·복원 중심 검증으로 한다. 기존 오류와 이번 변경으로 생긴 오류를 구분한다. 문서만 수정한 단계에서는 앱 빌드·DB 시험을 수행했다고 기록하지 않는다. Preview와 실기기 검증은 각각 별도의 증거가 필요하다.

## 9. 구현 전 남은 결정과 잠정값

추가로 사용자에게 즉시 물어야 하는 큰 방향은 현재 없다.

- 사용자 제공 HTML·CSS 저장본 분석은 완료했다. [소스 분석](references/namuwiki-source-analysis.md)의 미확인 동작만 후속 검증하며 동일 자료를 다시 요청하지 않는다.
- 서비스 이름·로고는 미정이며 임시 이름으로 시작 가능하다.
- 실제 본인 계정의 Supabase UUID는 구현 시 안전한 기존 계정 조회로 식별한다. 문서에 이메일만 적어 권한 기준으로 삼지 않는다.
- S25의 주 사용 브라우저·CSS viewport·확대/글자 설정은 실제 기기 시험 때 확인한다.
- 본문 크기·간격·색상·반응형 초기값은 원본 CSS 근거로 보정했다. 실제 폰트·S25 줄바꿈과 메뉴로 옮길 보조 목록은 구현 시 검증한다.
- 하루 1회 백업·보존 기간·허용 손실은 잠정값이다. 외장 하드의 경로·용량은 준비 후 확인한다.
- 기존 인증 래퍼 전환 범위와 운영 정책은 구현 전에 재검증한다.
