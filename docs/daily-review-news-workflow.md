# 데일리 리뷰 뉴스 · ChatGPT 직접 검토

## 실행 계약

- Python은 RSS 후보 수집·입력 검증·DB 저장만 담당한다. 별도 LLM API를 호출하거나 키워드 점수로 기사 중요도를 결정하지 않는다.
- ChatGPT/Codex가 이 작업에서 전체 후보를 읽고 시장 중요도 판단·사건 묶기·한국어 요약과 상세 설명을 직접 수행한다. `region`은 언론사/피드 국가 태그이며 기사가 다루는 시장 범위와 다르다.
- 출력 사건 수 상한은 없다. 전체 원문·RSS 본문은 DB에 영구 저장하지 않는다. 사건 요약·선별 이유·시장 범위·근거 기사 제목/출처/URL/발행 시각을 저장한다.

## 매일 실행

1. `.venv/bin/python3 scripts/daily_review_news.py collect` 실행. 기존 article-scrapper 전용 .venv를 사용한다. raw JSON/manifest는 `scripts/output/daily-review-news/`에 최신 스냅샷만 저장한다. 실패하거나 모든 후보가 없으면 요약을 지어내지 않는다.
2. raw JSON의 모든 제목을 작은 묶음으로 읽는다. 도구 출력이 잘린 부분은 다시 읽어 전체 검토를 완료한다. 후보를 키워드 필터로 먼저 제거하지 않는다.
3. 중요 후보의 요약과 시각을 읽고 같은 사건을 묶는다. 해외 사건은 해외 출처를 우선하되 국내 고유 정보도 포함한다. 해석·전망·확정 사실과 장중/종가를 구분한다. 제목뿐인 근거에는 `confidence`로 한계를 표시한다. 미해결 Google News 링크는 원문으로 해결됐다고 주장하지 않는다.
4. `/tmp`에 selection JSON을 작성한다. 필드: run_id, input_sha256, reviewed_article_ids(전체 후보 ID), excluded_article_ids(근거로 선택하지 않은 ID), exclusion_reasons(한국어 제외 이유 목록), events.
5. 각 events 항목: id(날짜 안의 안정적 사건 키), category(정책/기업·산업/경제), importance(핵심/주요), title, summary, details, reason, market_scope, confidence, article_ids(실제 후보 ID 목록).
6. `.venv/bin/python3 scripts/daily_review_news.py publish --selection /tmp/선별파일.json` 실행. 입력 hash/실행 ID/전체 후보 검토/선택·제외 분할/URL을 검증하고 저장한다. 이미 공개한 실행은 동일 내용 재실행만 허용한다. 수정하려면 새 수집 실행을 만든다.
7. `/api/daily-review/news?date=YYYY-MM-DD`에서 사건·수집 상태를 확인한다. 실패/검토대기/검토완료0건은 다른 상태다. 오류 시 기사 숫자만 보고 완전 수집이라고 판단하지 않는다.

## 저장·화면

- 테이블: `market_data.daily_review_news_runs`. 리뷰 날짜별 최신 수집 실행을 표시하고 이전 실행은 보존한다. 새 수집 실행이 PENDING이면 이전 결과를 오늘 최신 결과로 가장하지 않는다.
- Python publisher만 기존 service role로 쓰며 공개 쓰기 API는 없다. UI 서버의 읽기 API는 안전한 상태·사건·기사 링크만 반환한다.
- 뉴스 분류/안 읽음/브라우저별 읽음 표시는 기존 흐름을 유지한다. 핵심 사건 먼저 표시한다.

## 상세 설명 · 2026-10-14

### 다음 수집 실행부터 적용하는 상세 설명 기준

사용자는 현재 저장된 결과를 수정하지 않고 다음 자동 업데이트부터 상세 설명을 강화하도록 요청했다. 기존 실행을 enrich하거나 다시 발행하지 않는다.

- 목표는 근거 링크를 열지 않아도 사건 자체와 시장과의 연결을 이해할 수 있는 독립적인 설명이다. summary는 짧게 유지하되 details를 summary의 확장·반복으로 끝내지 않는다.
- 중요 사건은 RSS 요약만으로 충분한지 판단하고, 부족하면 실제 기사 링크를 열어 읽는다. 가능하면 공식 발표·공시·통계 원문과 관련 보도를 함께 확인한다. 원문이 유료벽·접근 제한으로 읽히지 않으면 접근 가능한 다른 근거를 찾고, 끝내 확인하지 못한 내용은 채우지 않는다.
- details에는 (1) 누가 언제 무엇을 발표하거나 실행했는지, (2) 처음 보는 사람에게 필요한 배경과 용어 설명, (3) 무엇이 이전과 달라졌는지와 확인된 수치·비교 기준·대상 기간, (4) 어떤 시장·업종에 어떤 경로로 영향을 줄 수 있는지, (5) 실제 관측된 시장 반응과 다음 확인 지점을 담는다. 자료가 없는 항목은 없음을 밝히며 모든 사건에 기계적으로 동일한 항목을 채우지는 않는다.
- 기본적으로 4~6개 짧은 문단, 한국어 약 800~1,500자 수준을 지향한다. 복잡한 사건은 더 길게 쓸 수 있고, 정보가 적으면 짧게 쓰되 부족한 근거를 명시한다. 분량을 맞추려고 일반론이나 검증되지 않은 사실을 덧붙이지 않는다.
- 기업 실적은 실제/예상/전년 및 가이던스의 기준을, 정책은 결정/제안/발효일·적용 대상을, 경제지표는 관측 기간·발표 시각·전월/전년·예상치 여부를 근거가 허용하는 범위에서 구체적으로 설명한다. 약어와 전문 용어는 처음 나올 때 풀어 쓴다.
- 사실·발언·해석·향후 시나리오를 분리한다. 시장 영향 경로는 해석임을 밝히고, 가격 반응이 확인되지 않으면 확인된 반응처럼 쓰지 않는다. 장중 변동과 확정 종가, 관측일과 발표일을 구분한다.
- 저장 전에 details만 읽었을 때 사건, 변화, 중요성이 이해되는지 확인한다. 다른 사건에도 그대로 붙일 수 있는 상투 문단, summary 반복, 근거 없는 인과관계는 다시 작성한다. 사용한 추가 원문은 기존 근거 기사와 대조하고 식별 가능한 출처를 설명에 남긴다.

- 각 사건에 `details`를 필수로 작성한다. 카드 본문 summary는 짧게 유지하고, 펼친 영역 맨 위에는 details의 문단별 상세 설명을 표시한다. 그 아래 선별 이유·불확실성·근거 링크를 배치한다.
- details는 사건의 확인된 사실, 배경·맥락, 아직 확인해야 할 부분을 설명한다. 제목이나 RSS 요약에 없는 숫자·사실을 추정으로 보충하지 않는다. 같은 summary의 단순 반복이나 고정 문구가 아니라 사건별로 직접 작성한다.
- 기존 공개 결과의 설명 보강은 `daily_review_news.py enrich --selection ...`로 수행한다. 기존 요약·선별 이유·근거 자료가 모두 동일한지 검증하고 details만 보강한다. 이전 사건 JSON hash와 보강 시각을 audit에 남긴다. 검토 시각을 이용한 조건부 갱신으로 동시 수정을 탐지한다.
- 현재 저장된 37개 사건 모두 2문단 이상의 상세 설명을 보강했다. API에서 details 반환과 기존 summary/reason 보존 확인. 관련 ESLint·프로덕션 빌드 통과. 매일 직접 검토 자동화에도 details 작성 규칙을 추가했고 실행 시간은 유지했다.

- 사용자 요청으로 뉴스 직접 선별 예약을 매일 06:00 및 15:00 KST로 변경했다. 기존 07:15 예약을 대체하며 수집·상세 설명·검증 규칙은 유지한다. 각 실행은 최근 24시간 후보를 새로 수집하고, 날짜별 화면은 최신 실행 결과를 표시한다.

## 근거 확보·발행 검증 개정 · 2026-10-16

다음 신규 실행부터 아래 절차를 사용한다. 기존 REVIEWED 실행은 수정하거나 재발행하지 않는다.

1. collect 후 전체 후보 제목을 끝까지 검토한다. 수량 상한·국가 할당·키워드 사전 필터를 두지 않는다. 초안 selection에 해당 run_id/input_sha256과 선정 사건별 실제 article_ids를 작성한다.
2. `.venv/bin/python3 scripts/daily_review_news.py prepare --selection /tmp/초안.json`을 실행한다. 선정 근거 전부에 대해 원문 URL 해결·페이지 조회·구조화 발행시각 추출을 시도한다. 새 shortlist 근거가 추가되면 해당 ID도 prepare한다. 별도 LLM API는 사용하지 않는다.
3. 출력된 temporary_texts 파일을 직접 읽는다. `text_available`은 본문 후보를 가져왔다는 뜻일 뿐 전문 확보·기사 일치·사실 검증·편집자의 읽기 완료를 보장하지 않는다. page_title/본문이 후보 사건과 일치하는지 먼저 확인한다. 광고·메뉴·접근제한 문구뿐이면 읽은 근거로 표시하지 않는다.
4. 원문 부족 시 공식 발표 또는 다른 확인 가능한 출처를 찾아 직접 읽는다. 추가 출처는 details에 식별 가능한 URL·문서명·관측일을 남긴다. 접근 제한을 우회하지 않으며 수치·종가·배경 사실을 제목으로 추정하지 않는다.
5. 실제 읽은 임시 본문 ID만 selection 최상위 `read_article_ids`에 작성한다. 핵심 사건에 읽은 후보 근거가 전혀 없으면 사건의 `verification_note`에 구체적인 미확인 사유 및 직접 확인한 추가 공식 URL 또는 부족한 항목을 작성한다. publisher가 confidence에 '추가 확인 필요'를 붙인다. 공식 자료를 읽었더라도 수집기의 후보 본문을 읽었다고 거짓 표시하지 않는다.
6. 최종 설명은 사건 자체·변화·중요성을 독립적으로 설명한다. 다른 기업의 별도 발표는 개별 사건으로 나누고 테마를 이유로 합치지 않는다. 미확인 사항·일반론으로 길이를 채우지 않는다. 800자 미만은 자동 탈락이 아니라 품질 점검 목록이며 근거에 맞춰 편집자가 판단한다.
7. publish는 모든 선정 후보에 prepare 결과가 있어야 진행한다. DB에는 URL·페이지 제목·발행시각 근거·조회 시각·본문 길이/hash·접근 상태와 편집자 읽기 신고를 저장한다. 본문은 임시 파일에만 두며 DB에 저장하지 않는다. 시간대 없는 날짜와 수정시각은 최초 발행시각으로 추정하지 않는다. 발견한 발행시각이 수집 구간 밖이면 배경 사건임을 설명하고 해당 표시를 유지한다. 원래 PARTIAL은 원래 입력 품질을 나타내므로 숨기지 않는다.
8. 새 collect/register는 후보 제목·출처·URL·발행시각 목록을 run별로 보존한다. RSS 요약·본문을 이 감사 목록에 저장하지 않는다. DB audit의 quality에는 조회 결과별 수·읽은 근거 수·짧은 설명·핵심 미확인 사건을 기록한다.

구현 범위: URL/시각/본문 확보 시도, 근거 메타데이터 및 품질 감사, 사건별 작성 규칙 강화. 신규/후속 화면 표시, 자동 공식 발표 일정 대조, 예약 슬롯별 모니터링 UI는 후속 과제이며 구현 완료로 보지 않는다. Google URL 형식·접근 제한 때문에 해결 실패할 수 있으며 실패를 '원문 확보'로 표시하지 않는다.

## 중복 감소 · 2026-10-27부터

최근 24시간 수집과 전체 제목 검토는 유지한다. 같은 사건의 의미 있는 후속을 잃지 않도록 URL 일치·제목 변경은 **참고 표시**이며 자동 제외하지 않는다. 언론사 국가(`region`)와 시장 범위, 시각 누락과 지연 도착도 이전대로 구분한다.

1. `collect` 직후 `.venv/bin/python3 scripts/daily_review_news.py context --context-output /tmp/daily-review-news-context.json`을 실행하고 파일 전체를 확인한다. `baseline_events`는 새 실행 직전의 가장 최근 REVIEWED 결과, `baseline_date`는 그 리뷰 날짜다. `candidate_hints`의 `new`는 이전 후보 목록에 같은 정규 URL이 없다는 뜻이고 사건 자체가 새로운지 보장하지 않는다. `seen`은 URL과 제목이 같다는 뜻으로 본문 불변을 보장하지 않는다. `title_changed`, RSS 요약 해시가 달라진 `content_changed`, `unknown`은 특히 수동 확인한다. 해시가 없는 과거 목록과의 비교에서는 내용 변경 여부를 알 수 없다. 목록이 없어도 후보를 버리지 않는다.
2. 이전 사건과 모든 후보를 검토해 AI가 사건 단위로 직접 비교한다. 같은 사건의 동의어·언어 차이·다른 언론사·속보와 종합 보도는 묶되 서로 다른 기업/정책/발표를 강제로 합치지 않는다. 새 보도가 있더라도 추가 사실이 없다면 새 사건으로 싣지 않는다. 계약 확정, 실적, 법안 의결, 종가 등 실제 변화가 있으면 기존 사건 ID를 유지하고 무엇이 달라졌는지 근거를 확인한다. 신규 기사는 사건·시장 중요도를 기준으로 선정한다. 전날에 이미 다룬 내용도 실질적 진전이 없으면 오늘 다시 신규로 쓰지 않는다. 기존 기사라도 제목 변경, 수정, 추가 공식 자료로 중요한 새 사실이 확인되면 후속으로 다룰 수 있다.
3. 선택 JSON에 `update_mode: "incremental"`과 context의 `baseline_run_id`(없으면 null)를 추가한다. 이번 실행에서 새로 다룰 사건만 `events`에 작성한다. 모든 사건에 `update_state`는 `new` 또는 `updated`, 후속은 기존 ID와 사실에 근거한 구체적 `update_note`를 필수로 넣는다. 이전 사건을 복사해 새 근거인 척 표시하지 않는다. `article_ids`는 이번 raw 후보 ID만 넣고 선택 기사 전부를 prepare한다. 핵심 기사에 읽은 원문이 없으면 검증 사유를 남긴다. 전체 제목 검토와 제외 ID 검증은 그대로다. 새로운 사건도 후속도 없다면 events는 빈 배열일 수 있다.
4. publisher는 같은 날짜의 이전 REVIEWED 사건을 자동으로 이어받고, ID가 같은 후속으로 교체하며 새 사건을 추가한다. 이전 날짜의 변경 없는 사건은 가져오지 않는다. 이전 근거 링크는 후속의 근거에 함께 보존하며 원문은 저장하지 않는다. 그 사이 기준 REVIEWED 실행이 바뀌면 발행을 중지하므로 context부터 다시 확인한다. 기존 REVIEWED 실행은 변경하지 않는다. 오전 사건이 포함된 오후 스냅샷은 신규·후속·이전 수집을 구분하고 후속은 새 읽음 상태를 가진다.
5. 발행 뒤 API에서 신규·후속·이전 사건, 원래 근거와 이번 근거, audit의 선택·제외 분할 및 실제 읽음 표시를 확인한다. 확인 불가능한 새 사실을 추정하거나 중복 여부를 확신할 수 없는 기사를 자동 제거하지 않는다.
